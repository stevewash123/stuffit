## Logging (added 2026-10-04)
- Every API call logs one summary line when it finishes (`ApiLoggingMiddleware`): method, path, status, ms, user, account, trace id (5xx at error level, the rest information). The trace id is also in the error body, so a report can be matched to its line.
- Exceptions bubble up and are logged once, in `ApiExceptionHandler`: a refusal turned into a 4xx is a warning (what, where, who, no stack), anything else an error with its stack. No catch-and-log-and-rethrow anywhere; a catch logs only when it swallows the exception on purpose (a bad upload in a batch, an unreadable email, a race that another call won). The framework's own line for the same exception and EF's failed-query lines are switched off in `appsettings.json` so there is no second copy.
- Every controller action logs its inputs first (`InputLoggingFilter`, registered globally): Development logs the values, with secrets masked by field name and long text cut; elsewhere it logs only field names, ids, numbers and flags, never typed text. `Logging:RequestInputs` = Off, Names or Full overrides it. Sign-in and two-factor calls never log values. Files are logged by name and size. The masking rules are `StuffIt.Core/Logging/InputRedactor.cs` (unit tested).
- Development prints one readable line per entry; other environments print JSON lines. EF's SQL text is at Warning in Development (set `Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command` to Information in `appsettings.Development.json` to count queries).
- At startup in Development the API warns if the database is missing migrations (the cause of the 500s on the to-do and insurance cards: `insurance_policies` and `todos.ref_id` did not exist until `dotnet ef database update` was run).
- Dev command: `--time-new-items <email>` times the New Items list; `--seed-new-items <email> <SampleData>` reseeds it.
