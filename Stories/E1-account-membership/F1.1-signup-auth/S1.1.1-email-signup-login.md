# S1.1.1 Sign up and log in with email

**Feature:** F1.1 Signup & authentication  
**Phase:** MVP  
**Milestone:** M1  
**Depends on:** S7.5.2 (DDL: account, user and billing schema); S7.6.1 (Environments and deployment)  

As a **new user**, I want to create an account with email and a password or magic link.

## Acceptance criteria
- Signup creates the user, an account and the membership in one transaction; membership role defaults to member
- Email and password (10+ characters, no composition rules); duplicate email is a 409 ProblemDetails
- Access token: 15 minutes, claims limited to sub, email, jti, account_id (docs/api-conventions.md)
- Refresh token: httpOnly cookie (path /api/auth), rotated on every use, stored hashed; reusing a rotated token revokes all of the user's sessions
- Login: generic failure message for unknown email and wrong password; lockout after 5 failures for 15 minutes
- Logout revokes the refresh token; GET /api/me returns the user and account
- **No account until the email is verified (decided).** Signup collects email, password and terms, stores a pending signup (password already hashed, expires in 24 hours, one per email) and sends the verification link. Nothing else exists yet: no user, no account, no private address, no sign-in. Opening the link creates the user, account and membership in one transaction, marks the email confirmed, and signs the person in, landing on the welcome page (S9.1.7). A resend is offered; an unverified address that is signed up again just gets a fresh link. Pending signups are deleted when they expire.
- The page after signup says "Check your email" and shows the address, with resend and "wrong address? start again"
- Someone invited by a head of family (S1.3.4) is already verified by following the invite link, so they skip this step
- Rate-limited auth endpoints; every endpoint requires sign-in unless marked AllowAnonymous
- Responses are unwrapped bodies; errors are ProblemDetails

## Status
Verify-first signup built (October 2026): `POST /api/auth/signup` holds a pending signup and emails the link (202); `POST /api/auth/verify-signup` creates the user, account and membership and signs in (201); `POST /api/auth/resend-signup` (always 204, not more than once a minute); expired ones purged daily. UI: "Check your email" view with resend and start again, and `/verify-signup`, which lands on /welcome. The older `verify-email` endpoint stays for people who signed up before this. Not built: the welcome email, and invite links skipping verification (S1.3.4).

Sign in with Google built (October 2026): `GET /api/auth/providers` tells the page the Google client id (the button is hidden when `Google:ClientId` is not set); `POST /api/auth/google` checks Google's signed identity token on the server (signature, expiry, audience). Google has proved the address, so no emailed link. A new person gets a confirmed account with no password once they agree to the terms (the page asks only when the server says an account is about to be made). A password account is signed in and linked only if its email was confirmed, so an unconfirmed pre-registration cannot be kept alive through Google. Administrators with two-step sign-in must use their password and code. A Google-only person deletes their account by typing their email (no password to ask for), and can set a password by resetting it. Setup: create an OAuth client id (Web application, with the site's address as an authorized JavaScript origin) in Google Cloud and put it in user-secrets as `Google:ClientId`. Not built: Apple or other providers, linking or unlinking Google from Settings.

Implemented in StuffIt_API (branch m1-auth). Auth provider decision: ASP.NET Core Identity + JWT.

**Stubbed:** the verification email is written to the API log only (`LoggingEmailSender`) until S7.6.4 adds a real provider, so a new signup cannot receive its link. Development workaround: `dotnet run --project src/StuffIt.Api -- --create-user email password [--operator]` creates (or repairs) a user with the email already confirmed.
