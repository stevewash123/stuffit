# T2 Document handling: happy-path test plan (matrix)

**Type:** Testing playbook, not a product feature. Draft 2026-10-21.
**Scope:** what a user uploads (PDF files and photo scans), in what order, and which SampleData file proves each step. Email-on-setup is a separate suite; this one is uploads only.
**Setup for every flow:** a new user with one credit card ending **1212** (most sample receipts show 1212; a few show 1111 or 7711, which is the "different card" case).
**Which files go together** (same item, maker, store; returns; generic warranties sharing a model): `Testing/SampleData/INVENTORY.md`, regenerated by `node Testing/SampleData/_tools/make-inventory.js`.
**Runners:** `key-viewer.html` (receipts, answer key), `warranty-viewer.html` (documents, five modes). Folders: receipts in `Testing/SampleData/receipts/{pdf,pdf-as-jpg,paper-photo}`, documents in `Testing/SampleData/warranties-from-receipts` (20, keyed in `index.csv`) and `Testing/SampleData/warranties` (18, keyed in `index.csv`).

## 1. What a person uploads, in the order it usually happens

| # | When | Document | Where it usually goes | Format they have |
|---|------|----------|-----------------------|------------------|
| 1 | Day 0 | **Purchase receipt** (store thermal, invoice, emailed receipt, order printout) | New Items (Add Item / drop files) | Photo of paper (phone), PDF from email, screenshot |
| 2 | Day 0 to 7 | **Protection-plan document** (Geek Squad, Home Depot Protection Plan, AppleCare, Allstate) | The item, in New Items; but often My Items or loose | PDF from email, photo of the mailed contract |
| 3 | Day 0 to 30 | **Manufacturer warranty** (card or booklet from the box, PDF from the maker's site) | The item (My Items detail page) | Photo of the card, PDF |
| 4 | Day 0 to 30 | Gift receipt, delivery or install invoice (separate from the sale) | New Items | Photo, PDF |
| 5 | Within the return window | **Return or exchange receipt** (refund, store credit, restocking fee) | New Items or the item | Photo, PDF/email |
| 6 | Years later | **Repair invoice or claim paperwork** | The item | Photo, PDF |

People do these out of order: the plan before the receipt, a warranty with no item, the same receipt twice, a photo and the PDF of the same receipt, one batch of ten mixed files. The matrix covers those in sections C and D.

## 2. The dimensions

- **Format:** PDF upload (`pdf/`), photo scan of a PDF (`pdf-as-jpg/`, same numbering), real phone photo of paper (`paper-photo/`).
- **Entry point:** New Items upload, My Items "Add" popup, item detail page, loose upload (no item chosen).
- **Item state when a document arrives:** waiting in New Items, kept in My Items, none.
- **Content shape:** one item, several items, a long receipt, a plan line, a return, a non-warranty receipt.

**Test cases, one per row (file, mode, expected, result column):** `T2-test-matrix.csv` here, 313 rows, generated by `Testing/SampleData/_tools/make-test-matrix.js`.

## 6. Matrix D: refusals and bad input (always run, cheap)

| ID | Input | Expect |
|----|-------|--------|
| D1 | Corrupt or password PDF | Clear message, nothing saved |
| D2 | Blank page, blank photo | "Could not read this" |
| D3 | Photo of something that is not a receipt (use a non-receipt JPG of our own) | Rejected plainly |
| D4 | Wrong file type (.docx, .txt) | Refused with the allowed types |
| D5 | Over the size limit | Refused with the limit |
| D6 | Over the user's daily AI cap | Told when it resets, nothing lost (see S2.4.13 cap work) |

## 7. How to run it

1. Fresh user, card 1212 (runner has "Clear New Items"; `--clear-items` clears everything).
2. A and B by the two runners, PDF twin then photo twin; record ✓/≈/✗ per row.
3. C by hand or as a scripted runner mode (reuse `modes_check.js` shape); D by hand.
4. Anything ✗ goes into `issues.md` with the file name; ≈ is eyeballed against the key.
