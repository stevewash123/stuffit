# S4.5.4 Actionable notifications

**Feature:** F4.5 Notification Center (in-app)  
**Phase:** v2  
**Milestone:** M7  
**Depends on:** S4.5.3 (Notification Center page)  

As a **user**, I want to answer a prompt right from the notification.

## Acceptance criteria
- A notification can carry inline actions such as Confirm, Update or Not sure (used by S6.3.3 card policy change confirmation)
- Completing an action sets action_status to completed, records who and when, and marks the notification read
- Failed or cancelled actions show their final state, not a dead button
- Already-handled or expired prompts show the outcome
- Same action set available from the email deep link
- Pending actions count toward a needs-action total

- A notification type that asks something of the user is created Pending (an `Actionable` flag on the notification request, set per catalog type)
- Resolving the underlying thing completes its pending notifications by reference, with no click on the notification needed: `CompleteByReferenceAsync(referenceType, referenceId, status)` sets Completed, who and when, and marks them read
- Deleting the thing, or its window passing, sets Cancelled instead
- Acknowledge also marks the notification read

## Notes
ConsignmentGenie uses ActionStatus for dropoff manifests and approvals. Its `CompleteNotificationActionAsync(referenceId, referenceType, completedBy)` is the part to copy: every handler that resolves the thing calls it, so the notification and the thing cannot disagree. See `docs/consignmentgenie-notification-center-review.md` section 3.

First resolvers to wire: to-do done or dismissed (S4.6), card benefits confirmed (S3.3.2), coverage check-later reopened. Types that should be Actionable: things_to_do, card_benefits_to_confirm, purchase_needs_info, receipt_unreadable, coverage_check_later, policy-change types.

## Status

Built 2026-10-06 (API only, no migration): `Actionable` on a catalog type (and an override on the request) creates the notification Pending; `INotificationService.CompleteByReferenceAsync(referenceTypes, id, status, userId)` sets Completed or Cancelled with who and when and marks it read. Wired: to-do done or dismissed → Completed, to-do deleted → Cancelled (`things_to_do`); card benefits confirmed → Completed, card deleted → Cancelled (`card_benefits_to_confirm`). Joined to-do batches are not actionable. Acknowledge now also marks read. Only these two types are Actionable so far: the others in the list below have no resolver yet and would sit Pending forever. Tests in `ReminderNudgeTests`; API integration 351.
Quick answers built 2026-10-06 (API and UI, not browser-checked): a pending notification lists its `actions` (`NotificationActions.For`: to-do nudges offer done, snooze, dismiss; card nudges offer not-now), `POST /api/notifications/{id}/actions/{key}` does what the thing's own page would do and returns the notification as it is now; an already-handled one is a 409 that says so, a to-do or card that is gone cancels the notification. The page shows the buttons (Done, Remind me later, Dismiss, Not now) and swaps in the answer without a reload. Tests: `ReminderNudgeTests` (2 more), `notifications.page.spec.ts` (3); API integration 353, UI 687.
Not built: the same actions from the email link (needs a signed link or a sign-in first); Cancelled on a passed window; the other types (purchase_needs_info, receipt_unreadable, coverage_check_later, policy-change) and their resolvers. The UI already shows the needs-action filter and badge.
