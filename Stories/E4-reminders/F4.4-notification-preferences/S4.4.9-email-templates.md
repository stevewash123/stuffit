# S4.4.9 Email templates

**Feature:** F4.4 Notification preferences (message type x channel)  
**Phase:** MVP  
**Milestone:** M4  
**Depends on:** S4.4.1 (Message type catalog); S7.6.4 (Transactional and inbound email)  

As a **operator**, I want to consistent, editable emails per message type.

## Acceptance criteria
- One template per message type: subject, HTML body, plain-text body, variables documented in the catalog
- Shared layout with header, footer and the compliance block
- Templates stored as files or records, not inline strings in code
- Preview and test-send from the admin console or a script
- Missing variable fails the send visibly in logs, not silently
- Every substituted value is HTML-encoded in the HTML body: a purchase named `<b>x</b>` renders as text, with a test

## Notes
ConsignmentGenie NotificationTemplateService builds HTML from inline strings per type.

## Status

Done (M4, API): `EmailTemplates` engine and 12 template files under `Infrastructure/Notifications/Templates` (embedded), one per template key plus `_layout.html` and `_layout.txt` carrying the header and compliance footer. Variables: title, message, actionUrl, actionLabel, settingsUrl plus any value the notification carried. A missing variable or template throws (the dispatcher records the email as failed and logs it). User text is never treated as template syntax. Preview and test-send: `--preview-email <type>` and `--test-email <type> <to>`. Not yet: an admin-console preview (operator UI later). Tests: unit `EmailTemplatesTests`, `NotificationEmailBuilderTests`.
