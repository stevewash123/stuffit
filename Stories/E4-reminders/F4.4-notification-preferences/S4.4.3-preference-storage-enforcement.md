# S4.4.3 Dispatcher: store preferences and enforce them on every send

**Feature:** F4.4 Notification preferences (message type x channel)  
**Phase:** MVP  
**Milestone:** M4  
**Depends on:** S4.4.1 (Message type catalog); S7.6.4 (Transactional and inbound email); S4.5.1 (Notification record and API)  

As a **system**, I want to respect the grid on every notification, for every channel.

## Acceptance criteria
- Preference rows keyed by (user, message_type, channel) with enabled flag; per-type delivery mode and lead time/threshold stored beside them; one model, not a matrix plus separate per-type flags
- Dispatcher always writes the notification record first (S4.5.1), then fans out to channels according to preferences; the in-app record is the source of truth and email/SMS are deliveries of it
- Mandatory types bypass preferences
- A type with no preference row falls back to the catalog default, never to enabled-by-default
- Bulk senders (digest and batch jobs) load preferences for many users in one query
- Preferences read from the database with a short in-memory cache; no preference bits packed into login tokens, which go stale until refresh and cap the number of types
- Per-channel delivery tracking on the notification: email sent/failed/bounced with timestamps, SMS likewise, so failures can be retried and audited
- Suppressed sends are logged with reason

## Status

Done (M4, API): `INotificationService` (`StuffIt.Core/Notifications`) implemented by `NotificationService` (Infrastructure). Writes the record first, then email per preferences; mandatory types bypass; no preference row falls back to the catalog default; preferences cached 60 s per user (`InvalidatePreferences` after the grid saves); bulk method loads preferences and addresses in one query each; email status sent/failed on the record, failed emails retried hourly for 24 h by a Hangfire job; suppressed sends logged with reason. Not yet: SMS (M8), digest/weekly delivery modes (M6, the modes are stored but ignored), unsubscribe link (S4.4.8), templates (S4.4.9, a plain renderer stands in). Tests: `NotificationDispatchTests.cs`, including a guard that only auth and the dispatcher use `IEmailSender`.

Update: a row is ALWAYS written (Steve, 2026-10-01). In-app preference off sets `is_hidden` on the row: never listed, counted or changeable via the API. Mandatory system alerts are never hidden; they stay until the user acknowledges and then deletes them (delete before acknowledge returns 409). Retention cleanup (S4.5.8) must never auto-purge a system alert.
