# S4.2.3 Digest batch job

**Feature:** F4.2 Digests and consolidated notifications  
**Phase:** v2  
**Milestone:** QA  
**Depends on:** S4.4.3 (Dispatcher: store preferences and enforce them on every send); S7.6.2 (Background job scheduler)  

As a **system**, I want to build and send digests on time, exactly once.

## Acceptance criteria
- Hourly job selects users whose local digest time is now; weekly digests use the same job filtered by weekday (not seven separate jobs)
- Each run is recorded: batch type, date, targets, successes, errors, duration; a user already processed for that date is skipped
- One failed user does not stop the rest
- Preferences and notifications loaded in bulk, not per user
- Output goes through the dispatcher (S4.4.3) so the grid and mandatory rules still apply

## Notes
ConsignmentGenie NotificationBatchService: daily 3:00, weekly 3:30 registered as seven recurring jobs, monthly; CanProcessBatch/RecordBatchProcessing for idempotency. Its cron runs at fixed UTC times with no per-user time of day.

## Status

2026-11-02 (feat-digest, API, not merged): Done for the daily digest; weekly is not built. `DailyDigestJob` is registered as recurring job `send-daily-digests` at minute 30 every hour (after the reminder job at :00, so that hour's reminders are in it). Selects people with held notices whose own digest time has passed today; the digest notification id is made from person + local date, so a person already done for the date is skipped and a rerun sends nothing. One person failing is caught and the rest go on. Held notices, people, preferences and today's digests are loaded in bulk (one query each); the send goes per person through `INotificationService` so the grid and required-notice rules apply. A `batch_run` row (batch type `daily-digest`, targets, successes, errors, duration) is written for every run that had anyone waiting, not for empty hourly runs. UAT trigger: `POST /api/maintenance/run-digest` (key-guarded, simulated clock only), returns text like "Digest run: sent 1, skipped 2 (nothing to report: 2), failed 0." No migration needed.

2026-11-06 (feat-weekly, API, not merged): Weekly done in the SAME job (`DailyDigestJob`, still `send-daily-digests` hourly at :30), not seven jobs. Per person it sends a daily digest for the types in daily mode and, on the person's local weekday (from their own digest time), ONE weekly digest for the types in weekly mode; a type is in one digest only (its current mode decides). Exactly once per local week: the notification id is made from person + the Monday of their local week (`WeeklyDigestId`), so a rerun, or another hour the same day, sends nothing. Missed that day = it waits for next week's day (no catch-up). Held notices older than 14 days are let go. If a person's weekly types ever carry different weekdays (only possible by editing the database; the grid keeps one), the later day waits a week. Each run writes a `batch_run` row for `daily-digest` and, when anyone weekly was waiting, one for `weekly-digest`. UAT trigger unchanged: `POST /api/maintenance/run-digest` (summary text adds "(N weekly)"). No migration.
