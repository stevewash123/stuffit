# S3.1.5 Default coverage for a pending item

**Feature:** F3.1 Coverage tracking  
**Phase:** v2  
**Milestone:** M6  
**Depends on:** S3.1.2 (Propose coverages when a purchase is saved); S2.2.5 (Pending items and their API)  

As a **user**, I want a pending item to arrive with the warranty and return coverage we already know applies.

## Acceptance criteria
- For a pending item, the same logic as S3.1.2 returns default coverages from the store's return policy, the matched card's confirmed benefits and the maker's warranty, as in force on the purchase date
- Each carries where it came from (`merchant`, `card`, `manufacturer`), a label, and the policy version it came from
- Recomputed whenever the item's store, date, card or maker changes (PATCH, Add Details)
- A missing date uses the received date and says so; no matched store or maker yields nothing from that source
- Accept (S9.9.3) stores these as the item's coverages, as a snapshot, same as a confirmed proposal
- Reuses `CoverageProposalService`; no second copy of the rules

## Status
API done (2026-10-02): `CoverageProposalService.ProposeForPendingAsync` runs the same core as S3.1.2 (refactored into one private `ProposeCoreAsync`, so there is no second copy of the rules); each coverage carries from (merchant / card / manufacturer), label, policy id and verified date. Recomputed on every GET and PATCH. A missing date uses the received date and says so (`dateAssumed` plus a note on each coverage). Accept stores the coverages as a snapshot with source Default. The New Items page still shows sample coverage until it is switched to the API.
