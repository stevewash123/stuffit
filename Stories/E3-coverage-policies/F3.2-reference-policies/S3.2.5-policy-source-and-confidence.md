# S3.2.5 Policy source and confidence

**Feature:** F3.2 Reference data & versioned policies  
**Phase:** MVP (part A); v2 (part B)  
**Milestone:** part A M5 (proposed, ahead of S2.2.2 going live); part B M7 with F6.1  
**Depends on:** S3.2.1; S3.2.3; S3.1.1 (coverage proposal); S2.7.2 (evidence for a fact)  

As a **user**, I want to know how far to trust a suggested warranty or return window, and as the **system**, I want every policy to carry where it came from, so suggestions are weighed by evidence and not treated as equal.

## Principle
Confidence is evidence, not a verdict. Each independent piece of evidence adds some; no single piece is certain; agreement from different people adds up. A person typing in a value is weaker than a person who uploaded the official document that came with the purchase. Several people doing the latter eventually outweigh one person searching the internet, because a search can miss things (a regional variant, a newer version, a category exception) and independent documents rarely all miss the same thing.

## Evidence ladder (starting weights, configuration)
| Evidence | Weight | Notes |
|---|---|---|
| Official source verified: operator or AI read the publisher's own page or document, with source link and date (S6.1.2) | 0.85 | The top single source. Not 1.0: pages change and can be misread. |
| Human internet search: an operator or the seed read it from the web and entered it | 0.75 | Can miss exceptions. This is how the current seed rows were made. |
| User supplied the official document and chose "it came with this purchase" | 0.50 | Per independent account. The document is stored as evidence (S2.7.2). Strongest user signal because it is the actual terms for that unit. |
| User chose from the list or confirmed a suggested policy | 0.20 | Echo of what we showed; counts only as a weak signal and never adds to the policy it echoes. |
| User typed the values in by hand | 0.25 | Single, unsupported. |
| Seed row marked "unconfirmed" (read from memory or a blocked page) | 0.30 | Replaced as soon as someone verifies it. |

## Acceptance criteria

### Part A: data model and seed (MVP)
- Each seller policy, manufacturer policy and card benefit stores its evidence: a list of source records (kind, account when it is a user, document id when there is one, source URL, read date, who entered it). The existing `source_url` and `verified_at` stay and are filled from the best record.
- Confidence is computed, not typed: combine the independent evidence for the same value as `1 - product(1 - weight)`. With the starting weights: one typed value 0.25; three independent users who typed it 0.58; one document-backed user 0.50; two 0.75; three 0.88, which is above one human search (0.75); an official-source verification alone 0.85, and with agreeing users it goes higher but never reaches 1.
- One account counts once per policy value, however many times it submits. Accepted suggestions (echo) do not count. Counted users need a verified email (same rules as S6.1.4).
- Bands for display: **Verified** (0.85 or more), **Likely** (0.60 to 0.84), **Unconfirmed** (below 0.60). The number is stored and kept in the API; the screens show the band with the plain reason ("Read from newbalance.com on Oct 3", "Reported by 3 people who attached their documents").
- Age lowers a band by one step when `verified_at` is older than the review age (default 12 months), until re-verified (S6.4.1). Nothing is deleted by age.
- Existing seed rows get an honest starting record: rows read from the publisher's page = human search (0.75) with the URL and the date; rows we could not read (New Balance return window, blocked sites) = seed unconfirmed (0.30), keeping their "confirm on the source page" note.
- New Balance gets a manufacturer warranty row (defect coverage on its own footwear), recorded as unconfirmed until its terms are read from the warranty page. Terms are not seeded from memory.
- The seeder keeps inserting only missing rows; confidence is recomputed from evidence, so it never needs hand edits.
- Admin screens show the evidence list and band for each policy, and let an operator add a verification record (S7.1.1).

### Part B: crowd claims (v2, with F6.1)
- Shared by default, with opt-out and redaction (S6.1.6). A document a person uploads backs their own coverage right away. Unless they turn sharing off or skip that document, the extracted facts (no personal data) are also recorded as a claim (S6.1.4), and a redacted copy of the document may be shared after the person has seen the preview
- Claims do **not** add confidence. Counting accounts only decides when an operator is asked to verify; verification adds the operator's evidence (official source or human search) to the policy and that is what changes the band
- The `UserDocument` weights above are kept for the day a person-verified document path exists, but nothing writes that evidence now
- If two different values for the same party and category are both claimed, nothing is averaged: the operator sees both side by side
- Official-source verification (S6.1.2) can still confirm any value at any count

### Use in suggestions (A and B)
- The coverage proposal carries the policy's band and reason with each suggested coverage, the same way extracted email fields carry confidence.
- Verified: suggested normally. Likely: suggested with "reported, not verified" wording. Unconfirmed: suggested only with a clear "confirm this" note and a link to the source; a single user's typed value is shown only to that user (S6.1.5).
- A coverage the user saved keeps its own snapshot (concept.md); the confidence at the time is part of it, and a later change in confidence does not alter it. If confidence drops or the value changes, S6.3.3 asks affected users.

## Notes
- Weights and thresholds are starting guesses, kept in configuration. Revisit after real corroboration data exists; the ladder order matters more than the exact numbers.
- This replaces the three fixed labels in S6.1.5 with bands derived from the same evidence; the labels there map to Verified, Likely and "Added by you".
- Document uploads as evidence must follow the privacy and retention rules (S2.6.x, S1.4.x): store the document under the user's own files; share only the extracted fact.
- Timing is not part of the confidence formula. A burst of independent users uploading the same new document may mean the policy changed; that is a diagnostic signal, handled in S6.3.1, which flags the current policy as "may have changed" instead of treating the burst as agreement.
