# S3.2.15 The category list follows the store

**Feature:** F3.2 Reference policies
**Phase:** v2
**Depends on:** S3.2.1 (party model); S3.2.7 (unverified stores); the Admin Companies page (`/admin/companies`)
**Related:** S3.2.16 (the list learns from what people pick); S3.2.10 (store brands)
**Found by:** Steve, 2026-11-10

As a **person adding an item**, I want the category list to lead with what the store I picked actually sells (Home Depot: tools, lawn and garden, appliances; REI: outdoor gear, winter sports, footwear), so I find the right one fast and do not scroll 38 unrelated kinds.

## What happens today
The Category dropdown on Add purchase (`add-purchase.page.ts`) and the item edit form (`item-detail.page.ts`) show one flat, alphabetical list of every category (`GET /api/categories`). The store plays no part. The brand picker already does the right thing in the other direction: brands known to make things in the chosen category come first and the rest still follow (`PartiesController.List`, `categoryId`). This story gives categories the same treatment.

## Acceptance criteria
- **A store can be linked to categories.** Shared data, not code: a link between a store and a category (many to many). Linking a category includes its children (REI linked to Winter sports covers Skis and snowboards, Ski boots and bindings, Helmets and goggles). Seeded for the main chains in `reference-data.json`, edited by an operator on the store's page in Admin Companies. The `--seed` run applies new links without touching existing ones.
- **A store with links gets a two-part list.** The linked categories first, then a divider, then an "Other categories…" entry that expands the rest of the list in place. Nothing is hidden or removed, only ordered.
- **A store with no links gets the full list, as today.** That covers general retailers (Amazon, Walmart, Target, Costco), new or unverified stores, free-typed stores and Private sale. An empty mapping is a valid answer, not a gap, and nothing prompts anyone to fill it.
- **No store picked yet gets the full list.** The list re-orders when the store is chosen or changed.
- **A saved or chosen category outside the store's list stays visible and selected.** Editing an item whose category is not one of the store's links, or changing the store after a category was picked, must never blank or hide the value. It shows where it would normally sit in the full list.
- **"Not sure" stays first** in every case.
- **The category guess is untouched.** Guessing from the item name (`CategoryGuesser`) still runs and can pick a category outside the store's links; the guess is applied as today and then shown selected.
- **Same behaviour in every place a category is picked:** Add purchase, the item edit form, and the New Items review. One shared ordering function, one set of tests.
- **Vehicles rule is unchanged** (retail never offers Vehicles unless the item already holds it).

## Design note
This links stores directly to categories rather than adding a "category group" layer. With about 38 categories and a hierarchy already in place, a group table is extra machinery; the child-inclusion rule gives most of the reuse. Revisit if the category list grows past what direct links can maintain.

## Out of scope
- Per-store ordering inside the linked list beyond alphabetical (S3.2.16 adds history-based order).
- Filtering brands by store.
- Using the store links to guess a category from a receipt (possible later; the guess today uses item words only).

## Tests (standing suite, deterministic)
- Ordering function: store with links; store without; no store; saved category outside the links; child included via parent link; "Not sure" first.
- API: category list/links endpoint returns the links; seeding is idempotent.
- UI: dropdown shows the divider and "Other categories…" for a linked store and the plain list for an unlinked one.
