# S6.4.8 Learn matching keywords from the documents the model had to read

**Feature:** F6.4 Other AI review sweeps  
**Phase:** future (unconfirmed)  
**Milestone:** unassigned  
**Depends on:** S7.6.5 (model wrapper); S6.1.1 (candidate queue, for the review step)  
**Found by:** Steve, 2026-11-10 (idea, captured as he said it; nothing built).

## The idea
Several places in the code find the part of a document they care about by matching words against a list, then read policy facts from that part. If the list finds nothing (or maybe even if it does), the document goes to the model. Teach the code to get better from that: after the model has read a document, ask it which words or phrases in the document pointed to what it found and are not yet in the list. Every uploaded document might add something. Over time the lists grow and fewer documents need the model.

Two constraints from Steve: do not let the lists grow so far that they bring back many false hits, and the model may need the full list to work with (so it does not suggest what is already there).

## Where lists like this exist today (to be checked when this is picked up)
`ServiceRecordRules` (powertrain words, not-covered words, recall and goodwill words), `MaintenanceRules` (task matching), `category-keywords.json` (item categories), `tracking-signals.json`, the receipt and email parsers, the company-page scouts (`LinkScout`, returns and warranty page finders), and the document-class wording in `document-kinds.json`. Each is a different kind of list with a different cost of a false hit.

## Thoughts recorded with the idea
- **The model proposes, a person approves.** A suggested word goes to a review list with the sentence it came from, the same way a shared-data candidate does (S6.1.1). Nothing joins a live list by itself. A false hit in a live list is silent and affects every account; a rejected suggestion costs a click.
- **Ask for a word only when it earns its place.** Propose a word only when (a) the model found the fact and the list did not, and (b) the same word appears in more than one document, or on one document with high confidence and a quoted sentence. A single odd word from one shop is noise.
- **Measure false hits before accepting.** Keep the documents already read as a regression set: the Scenario 69 and 68 orders, sample receipts, saved company pages. Before a word is added, count how many documents in the set it would newly match in a place it should not. A word that adds a false hit is rejected or narrowed (a phrase, or only with a second word).
- **Match scope matters more than size.** Many false hits come from a word that is right in one list and wrong in another ("tire" is upkeep on a car and a covered part on the tire part). Lists stay per purpose, and a suggestion names which list it belongs to.
- **Negative words are as useful as positive ones.** Ask the model the other way too: which words made the list match something that was not what was wanted. A "do not match" list with its own review.
- **Give the model a compact view of the list, not necessarily all of it.** The full list is useful so it does not repeat what exists, but long lists cost tokens on every call. Options: send the full list when it is under a size, and otherwise only the entries nearest the document's wording; or let the model suggest freely and have the code throw out suggestions that already match (cheap, and the model never needs the list).
- **Lists become data.** For this to work the lists move out of code into reference data in Neon (the make-it-data principle), versioned, with who approved a word, from which document and when. Several lists are already JSON files; the rest are string arrays in rules classes.
- **Watch the privacy line.** A suggested word comes from someone's document. Store only the word or phrase and the generic sentence shape, never names, numbers or addresses, and apply the S6.1.6 redaction rules before anything is shown to another person.
- **Record the lift.** Count how often the list alone handled a document before and after, and how often the model was needed. If a list's hit rate stops improving, stop asking for that list.

## Acceptance criteria (draft)
- After a document is read by the model, a job records suggested words per list, each with the sentence it came from, the document kind and a confidence. Duplicates of existing entries are dropped.
- An operator reviews suggestions on the Admin Data Review screen: accept (to a named list), narrow, reject, or mark "do not match".
- Accepting runs the regression set first and shows any newly matching documents.
- Lists are reference data with history; the rules read them from there.
- A report shows, per list, how many documents it handled alone before and after, and how many suggestions were accepted and rejected.

## Open questions
- Which lists are worth starting with: the repair-order rules (where Scenario 69 already shows the misses), item categories, or the company-page scouts?
- Whether the model is asked on every document or only on those the list missed (cost versus finding "matched, but for a different reason").
- Who reviews (Steve, or an operator role) and how much per week is tolerable.
