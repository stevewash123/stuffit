# S6.3.1 Scheduled job detects crowd-reported changes

**Feature:** F6.3 Automated policy-change detection & user confirmation  
**Phase:** v2  
**Milestone:** M7  
**Depends on:** S6.2.1 (Log coverage observations); S7.5.4 (DDL: curation and learning schema)  

As a **system**, I want to notice when many independent users change the same benefit the same way.

## Acceptance criteria
- Runs on a schedule; clusters edits by (issuer, card product, benefit kind, new value)
- Fires at a threshold (e.g. 10 distinct accounts, within a time window, agreeing on one value)
- Counts distinct accounts only; one household or one account repeating does not add votes
- Ignores accepted defaults (echo); counts user-edited values only
- Can weight by account age or paid status to resist sock-puppet manipulation
- Creates a change_signal record with evidence, never edits reference data directly
- Burst of the same new document: when several independent accounts upload a document for the same party and category within a short window (default 14 days, configuration) and it differs from the document or value on file (different file fingerprint after normalizing, or a different extracted value or version/date), raise a change_signal marked "possible policy change". Timing is the signal: the same count spread over years is just corroboration (S3.2.5) and does not fire.
- A burst is not counted as agreement for confidence. It does not raise confidence in the new value; it flags the current value for checking (S6.3.2 reads the official source) and shows the existing policy as "may have changed" until resolved.
- Same rules as above for distinct accounts, echo and sock-puppet weighting; uploads of the same document by one household count once.

## Notes
Covers edits to values and uploads of documents; the burst case came from the S3.2.5 discussion (policy source and confidence). Timing is a diagnostic input here, deliberately kept out of the confidence formula.
