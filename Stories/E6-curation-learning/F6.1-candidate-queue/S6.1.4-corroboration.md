# S6.1.4 Claims are counted; enough accounts sends one to an operator

**Feature:** F6.1 Candidate policy queue  
**Phase:** v2 (built 2026-10-26: policy claims, counting, the operator list, approve and reject; 2026-10-27: persisted name and alias claims, return policy on approving a store)  
**Milestone:** M7  
**Depends on:** S6.1.1; S6.1.3 (sharing is the default)  

As a **system**, I want to count how many different accounts have uploaded the same store name, brand, alias or policy, so that an operator is asked to verify it once enough have.

## Principle
The counter is a trigger for review. It is not evidence and does not change confidence. Until an operator verifies a claim, no other user sees it, and nothing in it is suggested to anyone. The uploader's own coverage works from their private data as before.

## Acceptance criteria
- A **claim** is one extracted fact about shared data: a store or brand name (entity), another name for a shared store or brand (alias), or a policy (return window or warranty). It holds the normalized key, the facts, and a status: collecting, ready, verified, rejected, merged. It never holds a document, a file, an order number, a price, a card or an account detail
- Every upload writes the user's own record first, then upserts the claim and adds the account to it (**claim accounts**: claim id, account id, date). The counter is the number of distinct account rows, so one account counts once however often it uploads, and removing an account (delete account) removes its row
- Policy key: same party, category (or "category unknown"), same value and start rule, with parts, as the fingerprint of the facts; near-duplicates are normalized. Entity key: the normalized name
- Accepted suggestions (echo) do not count: a claim comes from a document or a typed value the person supplied, not from picking what we showed
- At N distinct accounts (configuration, 3 for testing) the claim becomes **ready** and appears in the operator list. A claim already matching a verified shared value just records the agreement and does not need review
- A claim that differs from a verified shared value is not a competing policy: it is listed as a possible change for the operator (S6.3.1)
- Two claims for the same party and category with different values stay separate; the operator sees them side by side. Nothing is averaged
- Operator: list claims by status with counts, facts and sibling claims; approve (creates or updates the shared entity or policy with the operator's evidence, and marks affected waiting items for re-check); reject with a reason
- An on-demand **evaluate** (operator only) recounts and sets statuses; the same code runs on a schedule

Replaces the earlier text, where three matching submissions made a policy "community-reported" and raised confidence. Crowd agreement now only decides what an operator looks at.

## Names, aliases and the store's return policy (built 2026-10-27)
- A store or brand name, and an alias, is a **claim record** (shared_claims) with the accounts behind it (shared_claim_accounts: account and the spelling used, nothing else). It is made the first time any account holds the name. Each account keeps its own private copy; the claim only counts and carries the decision. Policy claims remain the pending candidate policies
- **Alias claims:** a name that starts with a shared store's or brand's name ("Gabe's Home Center" for "Gabe's") is suggested as an alias. That includes an order the store matcher already attached to the shared store on its first words. An alias claim is ready at one account (`Claims:AliasReadyAt`). Nothing becomes an alias until an operator approves it; approving adds the spelling to the shared entry and makes it an exact match for everyone
- **Approving a store or brand** creates a new shared entry (named as most accounts spelled it, or as the operator says) and points every account's copy at it; the private duplicates are removed and the accounts' own policies stay as private overrides. The other reading of the same name (alias or new entry) is closed
- **Return policy on approval:** approving a store can add the return policy the operator found: window in days or a description, runs from delivery or order date, restocking fee, and the page it was read on (required; it becomes the official-source evidence). Refused for a brand, for a warranty claim, and for an alias whose store already has a general return policy
- A rejected claim stays closed with the operator's reason; seeing the name again does not reopen it
- **A person's own policy that differs from the verified one:** their own policy still wins for them and is never changed. When a verified shared policy for the same store (or brand) and kind of item says something else, the coverage line carries one note: "Gabe's verified return policy is 30 days; yours says 45 days. Check which applies to you." Nothing is said when they agree or when the shared policy is not verified (built 2026-10-27)
- Not yet: asking the person "is this the same store?" (the store matcher attaches such names silently today), folding an account's own policy that matches the verified one away, and an operator screen for claims

## Approval: ping at 3, approve itself at 20 (decided 2026-11-01)
Approving every claim by hand does not scale, so the operator is asked first and the system finishes the job if nobody answers. This changes the principle above only in one way: a very large count may approve a claim, but it still never raises confidence beyond community-reported.
- **At 3 distinct accounts** (`Claims:ReadyAt`) the claim is ready and operators are pinged once. **Built:** the hourly `ClaimJob` ("evaluate-claims") sends every operator one in-app notification and email listing the ready claims, once per claim.
- **At 20 distinct accounts** (`Claims:AutoApproveAt`, default 20) a claim still waiting is approved automatically. **Built 2026-11-02** (API commit 6108b35): the hourly job runs it before pinging. It counts distinct accounts only; the verified-email and minimum-age rules are not applied, because the counting has neither. It approves manufacturer warranties and new stores, brands and card issuers; never aliases, card products, card benefits or plans.
- **Guards.** Automatic approval does not run when reports for the same party and category disagree on the value (values are never averaged), when the name is not a plausible business such as a person's name (S3.2.7), or when an operator has rejected the claim. Rejected stays rejected whatever the count.
- **What it publishes.** The value all the reports agree on, recorded as **community-reported** with the number of accounts and no source link. It is not Verified: an operator verifying against the official source (S6.1.2) still raises it and can correct or retire it afterwards. Each automatic approval is written to the audit trail as done by the system, with the count.
- **Needs more than the reports carry** (for example a return window with no days): the claim stays for an operator.
- **Open choices:** ping again if a ready claim sits for N days (suggested 7); whether 20 is right once there is real traffic; whether auto-approved entries are flagged for a spot check.
