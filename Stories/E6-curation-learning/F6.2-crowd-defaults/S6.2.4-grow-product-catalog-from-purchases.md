# S6.2.4 Grow the product catalog from what people buy

**Feature:** F6.2 Crowd-learned defaults  
**Phase:** future  
**Milestone:** Not planned  
**Depends on:** S2.4.1 (document reader); S2.4.3 (labelled set); S3.2.8 (product tree)  

As the **operator**, I want the names people's items go by, brand by brand, to be gathered and turned into catalog entries I approve, so that items link to a known product (its model, category and warranty rules) without my having to stage a large catalog by hand first.

## Why
Today an item's name stays as the reader gave it. The catalog it could match against is almost empty: a handful of fishing reels, and no entry for most brands (Husky, Whirlpool, Dyson). The matching code (`BrandMatcher.FindModel`, the product tree) works but finds nothing, so matching more cleverly at intake gains little. The names that real receipts produce are the best source for the catalog, and they are only seen once people use the app.

## The balance
Two pulls, and this story keeps both in check:
- **Test with things as they are.** While the app is being tried out, receipts with missing or unknown data are useful samples. The catalog is deliberately left sparse so the gaps show. Nothing here pre-fills or renames anything during that period.
- **Let the data grow, but not unreviewed.** A catalog staged in bulk by hand goes stale and is wrong in ways nobody notices. Entries come from real names, in the order they are seen, and only after an operator approves them.

So the work goes in stages, and each stage is safe to stop at:

1. **Gather (no effect on any item).** A report, run on request, lists per brand the item names seen across accounts, with counts, the model number when there was one, and the category the items ended up in. Names are normalized for the comparison only (case, spacing, punctuation, units such as "46 in." and "46IN"). It reads what already exists and writes nothing.
2. **Propose.** The report suggests groupings: names that are the same product written differently, and a suggested catalog name for each group. A group needs enough sightings, from more than one account, to be suggested. An operator accepts, edits or rejects each one. Accepted ones become shared catalog models (global, with the audit trail the other shared data has).
3. **Link at intake (never rename).** Once the catalog has real entries, a new item whose cleaned name matches a catalog model for its brand gets the model link, category and warranty node. The name shown stays as read. The match has its own confidence, below High, and the item is flagged as matched by name rather than by model number.
4. **Link what is already there.** The same matching runs over items already waiting or in My Items, as a one-off or on request, and fills only what is empty. Nothing a person set is changed.

## Acceptance criteria
- Stage 1 and 2: a command (or operator page) produces the per-brand report and the proposals; it makes no change to any item, purchase or account's data.
- Only names from items that were added to My Items, not waiting items or dismissed ones, count as sightings, so a misread that was thrown away does not become a catalog entry.
- A name seen in only one account is listed but not proposed. A private brand an account made for itself (S2.4.1) can be proposed for promotion to the shared list when several accounts have it.
- Accepting a proposal creates the shared model and its audit entry, and marks affected waiting items for re-checking, as other shared-data changes do.
- Stage 3 and 4: matching is by brand first, then the cleaned name; the longest whole match wins, and a tie finds nothing. A match never changes the item's name, never overrides a model number or category the person set, and records which way it matched.
- Deterministic and unit tested with plain names and a small catalog, no model call. The normalization rules are tested with real names from the labelled set (S2.4.3).

## Not in this story
- Renaming items to the catalog name. If it is wanted later, it is a suggestion the person accepts, not an automatic change.
- Seeding a large catalog by hand ahead of use. Brand seeding (house brands such as Husky, Kobalt, Kirkland) is separate and held until testing is largely done, for the reason above.
- Using the model to group names. Plain matching comes first; revisit if the report shows it is not enough.
- Warranty content for new catalog entries: that stays with the policy stories (S3.x, S6.1).
