Technical story.

## Design: one AI service interface, swappable behind it (decided 2026-10-03)
- The rest of the app talks to one small interface (for example `IAiService`: read a document for a property list with evidence, answer a question about text, classify) and never to a provider. The first implementation calls the Anthropic API with a key kept in secrets; a fake returns canned answers for tests and for running with no key; others can be added without touching callers. Spend caps, usage logging, prompt versions and the "never block the user" fallback live in a wrapper around whichever implementation is used, so they apply to all of them.
- Which implementation runs is configuration (`Ai:Provider`), and can differ per task (a cheap model for short receipts, a stronger one for long contracts).
- **A local model is a later option, not the start.** Reading scanned documents needs a model that can see pages, which is the heavy kind. As far as we know the host (Render) has no GPU machines, and a small model on its ordinary CPU servers would be slow and far less accurate on contracts; check what the host offers before planning on it. If privacy or cost ever requires it, the model runs on a separate GPU machine and a second implementation points at it. A cheaper step is the same hosted model through a cloud provider's own service for data residency, which is again just another implementation.
- A **no-model fallback** is worth building anyway: the deterministic parsers (S2.2.2's email reader) and plain OCR text with simple rules, so the app still fills in what it can when the AI is off, capped or down.

## Status

Partly built 2026-10-03 (API, unit-tested with no network; nothing here has talked to the real API yet because no key is set). Built: the interface `IAiProvider` and the wrapper `IDocumentReader` (`DocumentReaderService`), the Anthropic provider (`AnthropicAiProvider`, official SDK, structured output, PDFs and photos in, refusal handled as "not read"), the fake (`FakeAiProvider`), and the settings (`Ai:Provider` off, fake or anthropic; `Ai:AnthropicApiKey`; model per document kind, default `claude-opus-5-5`; per-account and global daily cost caps; prices per model). The wrapper refuses an empty, too-long or too-large request, reads the same document for the same properties once (by content hash), stops at the caps, turns every provider failure into "not read" with a reason, checks and tidies the values, and works out the cost from tokens. 33 unit tests in `DocumentReaderTests.cs`.
Built 2026-10-05: the ledger tables `ai_usage` (one row per provider call: account, kind, provider, model, pages, tokens, cost, status read, refused or failed, prompt version, UTC day) and `document_readings` (the result kept by hash, unique per account) with `EfAiLedger` (migration AiLedger, applied to dev and test), the registration in `Program.cs` by `Ai:Provider` (off, fake or anthropic; anything else stops startup), and the endpoint `POST /api/document-readings` (kind plus the ids of files already uploaded; `GET /api/document-readings/kinds` lists the kinds and their properties). Only the caller's own files can be named; an unknown kind, no files or more than 20 files is a 400 before any provider is called. Integration tests (`DocumentReadingTests`, 6): values with quote, page and confidence; cost logged once and a second read served from the store without calling the provider; refusal and failure come back as "not read" with a plain reason and are logged; provider off; the per-account daily cap (a document already paid for still shows); another user's file is a 404.
Still not built: reading files that are not stored yet (S3.4.1's "start from the document" needs an upload that reads the bytes and keeps no copy), the global-cap and failure-path admin view of spend, and S2.4.1's callers (S3.4.2, S3.4.1, S2.2.2). Nothing has run against the real API yet (no key set).

Provider wiring 2026-10-06: the provider is chosen in one place, `AiRegistration.AddDocumentReading` (`Ai:Provider`): `anthropic` (the real model, used in development until the reader is tested), `qa` (`QaAiProvider`: believable canned readings for receipts, plans and policies, same file reads the same way, every third receipt has a low-confidence total so the "not sure" path shows; used while QA'ing), `fake` (the test double, tests only) or `off` (default). Nothing else knows which is in use. Every integration test factory sets `Ai:Provider` to `off` (or `fake` for the reader tests) so a key in user-secrets is never used by the suite. Swapping from the real model to the QA stand-in is one setting. To drop the key later for identity federation, leave `Ai:AnthropicApiKey` unset: the provider already builds a key-less client (`new AnthropicClient()`), which picks up the federation environment variables.
