# S7.7.1 Split the pending-item service

**Feature:** F7.7 Code health  
**Phase:** MVP  
**Milestone:** M6 (first thing, before S2.2.2 and the S2.4.1 callers)  
**Depends on:** none  

As a **developer**, I want `PendingItemService` broken into small services with one job each, so the AI reader and the receipt-extraction work land in the right place and not in a bigger class.

## Why first
S7.6.5 (the wrapper, to be wired to uploads) and S2.2.2 (extraction) both add behaviour to this class. Adding it first makes the split harder and the diff unreviewable. Split, run the tests, then add.

## Acceptance criteria
- `PendingItemService` keeps only the list, get, accept, dismiss and restore of a pending item, and delegates the rest.
- New services, one per job (names indicative): ingest (upload and email in), reading (document reader and fill-in), processing (the stale/re-match queue), returns (return-window proposals). The existing partial files are the seams.
- No service takes more than about 8 constructor dependencies; no file over about 400 lines.
- Public API (routes, JSON) unchanged; no migration.
- All existing unit and integration tests pass with only the changes needed to construct the new classes. No new behaviour in the same change.
- Anything time-based uses `TimeProvider` (T1), not `DateTime.UtcNow`.

## Notes
Do it in steps, tests green after each: extract a service, move its callers, repeat.
