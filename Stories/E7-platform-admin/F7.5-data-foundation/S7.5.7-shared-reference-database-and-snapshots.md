# S7.5.7 One shared reference database, published to every deployment as a versioned snapshot

**Feature:** F7.5 Data foundation
**Phase:** MVP (alpha needs it to stay in step with Dev), then v2
**Depends on:** S7.5.1 (reference schema); S7.5.5 (migration tooling and seed scripts); S3.2.5 (policy source and confidence); F6.3 (policy change detection)
**Found by:** Steve, 2026-11-14 (spec: reference-db-spec.md on the share)

As an **operator**, I want one master database of public facts about stores, manufacturers and credit cards, filled by the crawler bots and handed to each deployment as a versioned snapshot, so Dev, alpha and production share the same reference data without ever reading each other live.

## Why
Reference data is now loaded by hand into each database, and the loads clash: a hand-loaded row trips `ex_manufacturer_policies_no_overlap` against the same policy arriving by import. Crawler bots will produce far more data than hand loads. A single master with a publish step keeps one source of truth, lets QA pin a known version, and keeps a bad crawl from hitting every site at once.

## Architecture
- **Master:** a new Neon project, `warrantycat-reference`, holding reference tables only, no accounts. The crawler pipeline is the only writer: WebCrawler1 crawls; PolicyPublisher writes proposals and approved rows.
- **Publish:** an export command writes a versioned snapshot (the `reference-data/*.json` format or a successor), tagged with a version and date.
- **Consume:** each deployment runs `--import-reference <snapshot>` (existing, idempotent). This also reseeds a deployment, and a deployment can pin a version so QA tests against a known one.
- **No live reads.** A bad crawl would reach every site at once, every deployment would need a second connection string, and Dev and alpha would stop being isolated.

## Acceptance criteria
### Stable identity
- Every company, category, card and policy has a stable natural key or ID, the same in the master and in every deployment.
- The import upserts by that key. It never duplicates a row and never trips the overlap constraints (the `ex_manufacturer_policies_no_overlap` clash with hand-loaded rows is designed out).
- A second import of the same snapshot inserts 0 and updates 0.
- The import reports inserted, updated and unchanged counts.

### Data gathered
- **Stores:** return window in days; what starts the clock (purchase or delivery); holiday extensions; category exceptions (electronics, opened, final sale); restocking fees; receipt or proof-of-purchase rules; refund, store credit or exchange. Also price adjustment or price match windows, store protection or extension plans, membership benefits. Also where to start a return: portal URL, phone, in-store accepted, return-by-mail instructions.
- **Manufacturers:** warranty length by category or product line; what is covered; exclusions; registration required; transferable. Where to start a claim: claim page URL, phone, email.
- **Credit cards:** extended warranty (extra time and cap), purchase protection, return protection; the benefit administrator's claim URL and phone; the guide-to-benefits URL.

### Tracking on every record
- **Sources:** source URL(s), capture date, and a content hash of each source page.
- **Crawl status:** `found_read`, `no_website_found`, `website_unreadable` (reason: PDF only, blocked, or login wall), or `no_policy_published`. Not-found results are stored as real, dated rows; they count as data and show the gaps.
- **Source label:** the master only ever sets "AI verified from company website - please confirm this matches your item."
- **Recheck:** starts at 90 days, tunable. A recheck compares the content hash; only a changed hash triggers a re-read (same rule as the in-app sweep).

### Source status inside a deployment
- "User confirmed from multiple uploads" (2+ distinct accounts) and "Reviewed by WarrantyCat administrator" are set only inside a deployment, never by the master.
- An import never overwrites or downgrades those. The one exception: the master marks the source changed (new content hash), and the policy then returns to AI verified.
- A policy with no source is not shown as coverage (existing rule).

## Deliverables
1. Master schema (can reuse the app's reference tables, plus crawl status, content hash and recheck fields).
2. Export command that writes a versioned snapshot.
3. Import changes: upsert by stable key, never downgrade, reset to AI verified on a changed source, report inserted/updated/unchanged.
4. One-time backfill of today's `reference-data` into the master.
5. A short write-contract note for WebCrawler1 and PolicyPublisher: fields, statuses, how to report not-found.

## Out of scope
- Regional variants (US only for now).
- Live reads from deployments.
- User-submitted data in the master.

## Tests (standing suite, deterministic)
- Import twice: second run inserts 0 and updates 0.
- Import over a hand-loaded identical policy: no overlap error, no duplicate.
- Import never downgrades Admin reviewed or User confirmed; a changed content hash resets to AI verified.
- Export then import into an empty database reproduces the same data (round trip).
- Not-found crawl statuses import as dated rows and show no coverage.
