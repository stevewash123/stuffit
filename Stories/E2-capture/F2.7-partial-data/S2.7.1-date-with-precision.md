# S2.7.1 A purchase date can be approximate

**Feature:** F2.7 Partial data and uncertain facts  
**Phase:** v2  
**Milestone:** M6  
**Depends on:** S2.1.1 (Add a purchase with one or more items); S7.5.3 (DDL: purchases, items and coverage schema)  

As a **user**, I want to say "about 2019" when I do not know the exact day.

## Acceptance criteria
- Date precision: exact day, month, year, a range (earliest and latest) or unknown; the form offers "Not sure of the exact date"
- Stored as an earliest and a latest possible date plus the precision; an exact date has both the same
- Who or what gave it is recorded (user said, email, receipt, serial decode, estimate); see S2.7.2
- Everything that reads the purchase date (coverage, reminders, lists, export) uses earliest and latest, never a made-up exact day
- Lists show it as the user said it ("2019", "Mar 2019", "2018 to 2020"), with an "estimated" mark
- Migration keeps existing dates as exact; purchase date is no longer required to be exact
- Pattern: any fact we can only partly know follows this shape (S2.7.2)

## Notes
Data change. Existing M3 code assumes one required date.

Done (2026-10-02, API and UI). Purchase carries DatePrecision and PurchaseDateLatest; PurchaseDate stays the earliest day so existing code keeps using the cautious end. Migration ApproximateDates applied to dev and test databases.
