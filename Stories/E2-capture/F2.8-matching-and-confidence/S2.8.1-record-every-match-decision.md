# S2.8.1 Record every match decision

**Feature:** F2.8 Matching and confidence  
**Phase:** v2  
**Depends on:** none

As a **operator**, I want every store, brand, return-policy and warranty match to leave a record of how it was made, so thresholds are tuned from data and not guessed.

## Acceptance criteria
- Each time the matchers bind or decline a name, a `match_decision` row is written: the printed text and its normalized form, the rule that fired (exact, alias, prefix, brand-in-line, keyword, user), the winner and its score, the runner-up and its score, the band, who finally chose (system or user), what was at stake (category, policy, warranty) and when.
- No behavior changes: the same names bind to the same parties as before. Existing matcher specs stay green.
- Rows carry the account only as an id; no receipt text beyond the printed name is stored.
- A read-only admin query (or export) shows the counts per rule and per band.

## Notes
First stage of the plan: no risk, and it gives every later stage a baseline. It also answers the review's open question about starting thresholds.

## Status
Built (Push 66, API only). Table `match_decisions` (migration MatchDecisions; no tenant filter, FK to the account with cascade so a deleted account takes its rows). Written by `MatchLog` through a short-lived context on the same connection, so it never touches the caller's pending changes, and a failure to write is swallowed. Recorded: every `PartyMatcher.FindSellerAsync` and `FindMakerAsync` try (document facts, item warranties, receipt reading) and the brand-in-line match in email intake. Rules logged: store `exact`, `key`, `alias`, `prefix`, `ambiguous` (a tie, nothing bound, both named), `none`; brand `key`, `alias`, `in-line`, `none`. Nominal scores (`MatchBands`): exact/key 1.0, alias 0.95, prefix 0.6, in-line 0.85 or 0.65; band high from 0.9, middle from 0.5, else low. `StoreNameMatcher.Match` returns the rule and runner-up; `Find` gives the same answer as before. Read-only `GET /api/admin/match-decisions/summary?days=30` (operator): counts per field, rule and band.
Not recorded on purpose: the typed `match-brand` lookup on the add form (a call per pause in typing would swamp the real decisions), and user picks (no pick exists yet; S2.8.5). The printed name is stored (cut at 300 characters) for the operator's tuning; nothing else from the receipt.
