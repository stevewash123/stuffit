# S2.2.2 Extract purchase details from email

**Feature:** F2.2 Email-in capture  
**Phase:** v2  
**Milestone:** M6  
**Depends on:** S7.6.5 (LLM integration and cost control); S2.2.1 (Unique inbound address per user)  

As a **system**, I want to turn a receipt email or PDF into structured purchase data.

## Acceptance criteria
- Returns seller, date, total, order number, line items, card last-4 when present
- Returns a confidence per field
- Handles multi-item orders as one purchase, many items
- Raw email retained for audit
- Order confirmations and shipping notices are first-class inputs, not second-best receipts: for online orders they are the common case (stores like Home Depot ask before emailing a receipt, and many people decline unless the item is an appliance or similar). Classify each email as confirmation, shipped, delivered or receipt. All of them for one order number update the same pending item or purchase (S2.2.4); none creates a second one. Each stage fills different fields: the confirmation gives order number, order date, total and an estimated delivery date; shipped and delivered give the real delivery date.
- Keep the delivery date when found. Return windows often run from delivery, not the order date, so the pending item should carry both and the return-window coverage should say which one it counted from.
- Partial results are normal: whatever is found is kept, whatever is not stays empty and shows under "Missing". Nothing is guessed to fill a gap the email does not cover.
- The system fills in what the shared data knows: the store matched to a known seller; the brand when the seller makes its own goods (New Balance, Apple); the category when the seller sells one kind of thing (a default category on the party); the card by its last four digits; the return window from the seller's policy, counted from delivery when the policy says so. Each filled-in value carries a lower confidence than a value read from the email.
- Raw email retained for audit, beside the pending item, and moved to the purchase on Accept or Add Details.
- A later email for an order already seen (shipped, delivered, a receipt) fills in what is still empty and replaces an estimated delivery date with the real one. It never overwrites a value the user typed, and an item already accepted or dismissed is left alone.
- Real sample (New Balance "Thanks for your order", 2026-09-28; the .eml holds a name and address, so keep a scrubbed copy for the fixture): it is an order confirmation sent before shipping, not a receipt. The seller is the From display name; purchase date = "ORDER DATE"; total = "Order Total" (not the item price or subtotal, which differ by discount and shipping); the order number is "ORDER #"; payment is "PayPal" with no card last 4, so the card stays unmatched; the item is only a model name and style number ("928v3", "Style #: MW928BK3"), no maker field. A shipping email follows later for the same order number, so it must dedupe against this one (S2.2.4). The email also quotes the seller return policy text.


## Status
Partial version done (2026-10-03, API and UI), without the LLM: a deterministic reader (`ReceiptEmailParser`, MimeKit) for order, shipping, delivery and receipt emails. Reads the sender name, order number, order date, order total, estimated or real delivery date, card last 4 and product names, with a confidence per field. It is used for an uploaded `.eml` (New Items, "Upload a receipt or email"); `PendingItemService.IngestEmailAsync` fills in the rest from the shared data and merges later emails for the same order (dedupe key = store + order number, so S2.2.4 is built as well). The New Balance sample is a scrubbed fixture at `StuffIt_API/tests/Fixtures/new-balance-confirmation.eml`. Reference data now has New Balance (seller and maker, default category Footwear, 30-day return from delivery, to be confirmed on its page; newbalance.com returned 403 to our fetch), a Footwear category, and a "return runs from delivery" flag on seller policies (set for New Balance, Amazon, Apple). Migration EmailExtraction applied to dev and test. 16 parser unit tests, 9 API integration tests, 3 UI specs.
Photos and PDFs read through the document reader (S2.4.1), built 2026-10-05 (API; tests pass; nothing has run against the real Anthropic API yet, only the fake provider, and the New Items screen only had its button wording changed to "Uploading and reading…"). After a receipt photo or PDF upload (several files, or the pages of one receipt with `together=true`) the stored, cleaned pages are read as kind `receipt` and the pending item is filled where it is empty: store (matched to a known seller by exact name, otherwise kept as typed text), order number, purchase date, total, delivery date (a date still ahead is marked an estimate), card last four (matched to the person's card), and the item line (brand, model and kind of product found from it, the same as for an email; several items become "first and N other items"). Each value carries a confidence from how sure the reader was (clear 0.85, check this 0.65, unsure 0.4); a value that failed its own checks (not a date, an impossible amount) is not used. It only fills empty fields, so nothing the person typed is replaced. A reading never blocks the upload: not switched on, over the daily limit, a provider failure, a refusal or an unreadable document all leave the item blank as before, with the receipt kept. The same file twice is not read twice (the duplicate check comes first, and the reader also keeps results by hash). Tests: `ReceiptReadingTests` (6).
It runs inside the upload request, not in the background: one request reads at most 5 receipts (`PendingItemService.MaxReadsPerRequest`), the rest arrive blank, because each read takes seconds and the person waits. Moving it to a background job needs a tenant for the job (account-owned rows are invisible without one) and a "reading" status on the pending item so the screen can show "Reading your document…".
A receipt that names an order we already have joins that item (2026-10-05): once the reader finds the store and order number, the item is keyed by its order exactly as an order email is (`order:<store>:<order number>`), so a photo and the emails for one order become one item, in either order. A receipt that arrives after the email fills only what the email left empty (the card last four, say), keeps what the email said, and its pages are added to the item beside the email; an email that arrives after the receipt lands on the receipt's item. The same receipt twice is a duplicate and its second copy is not kept or paid for; an item already in My Items or set aside is left alone. Tests: 4 more in `ReceiptReadingTests`.
Not done: the quote and page of each value are not kept with the item (the confidence is); the plain parser running before the model for known stores; the "find these terms" mode; the LLM reader for email layouts the label rules miss; a multi-item order becomes one pending item named "first item and N other items" instead of one purchase with many items; style number, size and color are not kept; no inbound address yet (S2.2.1), so an email gets in only by upload; the sender name is trusted as the store (no spoofing check); an email for an order that is already accepted does not update that purchase's delivery date; the seeder does not change existing rows, so the delivery flag on Amazon and Apple reaches a database only when its row is created.

Confidence gate built 2026-10-06 (API and UI, tested): a printed receipt is trusted. A value read with high or medium sureness goes in as read; one read with low sureness (below 0.5) still lands on the pending item, which is only a draft, but is listed in `check`. Quick add (`accept`) refuses with a message until the person has checked it, the New Items row says "Not sure of: ..." and the Add form says so; typing or confirming the value (PATCH) makes it their own and clears the flag. No migration. Values are not stored with their quote or page: the receipt image stays attached, so the person can look at it (an earlier plan to keep quotes was dropped).
