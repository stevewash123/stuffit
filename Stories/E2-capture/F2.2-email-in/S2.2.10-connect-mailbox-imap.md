# S2.2.10 Connect a mailbox with an app password (IMAP)

**Feature:** F2.2 Email-in capture  
**Phase:** MVP (recommended way in, shown first on the welcome page, S9.1.7)  
**Milestone:** next after S2.2.1 goes live; Gmail and iCloud first, other providers later  
**Depends on:** S2.2.5 (Pending items and their API); S2.2.2 (Extract purchase details from email); S2.2.9 (Guided forwarding setup)  

As a **user**, I want to link my mailbox in settings so StuffIt finds my order emails on its own, without me setting up forwarding.

## Why
This is the way we recommend first: nothing to set up in the mail app, and it also brings in the last year. Forwarding (S2.2.9) stays for people who do not want to give out a credential.

Reading a mailbox over IMAP is simple to build and needs no provider app review (unlike Gmail OAuth, S2.2.8). It also reaches custom-domain and ISP mailboxes that have no OAuth. The cost is a stored credential that opens the whole mailbox, so it carries rules.

## Acceptance criteria
- Settings > Email: "Link my mailbox" asks for the server, the address and an app password. Known providers (Gmail, Yahoo, iCloud, Outlook) prefill the server and link to how to create and revoke an app password
- The page says never to use the real account password. Where the provider offers OAuth we show that option first (S2.2.8)
- IMAP, not POP3. Fetching uses a server-side search on sender and subject patterns and reads with BODY.PEEK, so mail is never marked read, moved or deleted
- Only matching messages are downloaded. After classification (S2.2.2) anything that is not an order, shipping or receipt message is discarded, not kept
- Each kept message becomes a pending item (S2.2.5) with the same de-duplication as forwarded mail (S2.2.4)
- "Test connection" checks the login and shows how many messages match before anything is added. The first scan looks back a limited time (for example 12 months) and waits for the user's go-ahead
- Scans run on a schedule and by "Check now"; the last scan time, count fetched and any error are shown
- The stored password is encrypted with a key held outside the database, never logged, never returned by the API, and shown once at entry
- "Unlink" deletes the stored password at once; deleting the account does too; mail the user did not accept is deleted
- Login failure (revoked or expired app password, provider withdrew password access) stops scanning, tells the user in the app, and points to forwarding (S2.2.9)
- A household member's linked mailbox feeds only their own pending items (S1.3)
- Audit: linked, scanned (counts only), unlinked, with who and when

## Not in scope
- POP3 (can only download everything)
- Any write access: no sending, moving, flagging or deleting mail

## Open questions
- Whether to refuse a main account password by detection (not reliably possible) or only by wording
- Which providers still allow app passwords when this is built; re-check then
- Where the encryption key lives (Render secret vs a managed key service)

## Status
Built (first slice): Gmail and iCloud only, so the server is ours to name (no "other" server, which would let a person point us at any machine).
- Link on the welcome page: pick Gmail or iCloud, address and app password; "Check it works" counts order-looking emails from the last 12 months before anything is added; "Bring them in" links.
- IMAP over TLS (MailKit), inbox opened read-only, BODY.PEEK, server-side subject search; only matches are downloaded; messages over 5 MB are skipped. Each becomes a New Item through the same pipeline and de-duplication as forwarded mail.
- Scans run in the background: right after linking, on "Check now", and every two hours. Up to 200 messages per scan, oldest first, the place reached saved after each page; a longer backlog carries on by itself.
- Password encrypted with AES-GCM; key from `Mailbox:EncryptionKey` (base64, 32 bytes), else derived from the signing key. Never logged or returned. Unlink deletes it at once; account deletion removes it.
- A refused login stops scanning, shows the message in the app and points to forwarding. Counts-only audit (linked, scanned, failed, unlinked) outlives the link.
- Tests: cipher (unit); link, scan, isolation between users, revoked password, unlink (integration, fake mail server); component spec.

Not built: Yahoo, Outlook and other providers; Gmail "All Mail" (only the inbox is read); a Settings > Email page (the welcome page is where it lives for now); a push to the user when the login stops working (the app shows it); a poison-message guard (an email that always fails to read would hold the scan at that point and retry each run).
Production needs `Mailbox:EncryptionKey` set, or relinking is needed whenever the signing key changes. To verify with real accounts: the Gmail and Apple app-password steps and links, and IMAP search behaviour.
