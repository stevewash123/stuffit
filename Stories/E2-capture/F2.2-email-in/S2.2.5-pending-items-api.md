# S2.2.5 Pending items and their API

**Feature:** F2.2 Email-in capture  
**Phase:** v2  
**Milestone:** M6  
**Depends on:** S7.5.3 (DDL: purchases, items and coverage schema); S3.1.5 (Default coverage for a pending item); S2.1.1 (Add a purchase with one or more items)  

As a **system**, I want one place for partly captured purchases, whatever their source, so the New Items page and the capture paths share it.

## Data
`pending_items`: id, account_id, owner user, source (`email` | `receipt_upload`), source reference (inbound email id or document id), source label (subject or file name), received at, status (`pending` | `accepted` | `dismissed`), extracted name, store text and matched store party, date, total, order reference, card last 4 and matched card, a confidence per field, dedupe key (seller + order number, else a content hash), dismissed at, accepted purchase id. Migration with an index on (account_id, status).

## API (account-scoped; owner or household member per F1.3)
- `GET /api/pending-items?status=pending|dismissed` list, newest first, each with its default coverages (S3.1.5) and a list of missing fields
- `GET /api/pending-items/count` pending count for the tab badge
- `GET /api/pending-items/{id}` one item, for Add Details
- `PATCH /api/pending-items/{id}` correct fields; recomputes default coverage
- `POST /api/pending-items/{id}/accept` creates the purchase, item and coverages in one transaction; 409 with a problem if there is no default coverage; idempotent (a second call returns the same purchase)
- `POST /api/pending-items/{id}/dismiss` and `/restore`
- `POST /api/pending-items/{id}/complete` used by Add Details: saves the full purchase form and marks the pending item accepted in the same transaction
- ProblemDetails errors, camelCase JSON, per docs/api-conventions.md

## Acceptance criteria
- Another account's pending items are never visible (404)
- Accept, dismiss and restore are audited with who and when
- Integration tests cover each endpoint, the idempotent accept, the no-coverage refusal and cross-account isolation

## Status
API done (2026-10-02): `PendingItem` and `PendingItemEvent` (audit) entities, migration `PendingItems` (applied to dev and test), `PendingItemService`, `PendingItemsController` with every endpoint above, 9 integration tests (list/count/get, patch with store and card matching, accept with idempotency and a concurrent double tap, no-coverage 409, dismiss/restore, complete, cross-account 404, audit rows). Accept and complete run in one transaction; a `xmin` concurrency token makes the loser of a double tap return the winner's purchase.
Decisions: PATCH leaves null fields unchanged (an empty string clears text; dates and ids cannot be cleared). A pending item has no capture path until S2.2.2 / S2.2.6, so the screen has nothing real to show yet. Accepting an item with no date counts from the received date and writes that into the purchase notes. A receipt file is not yet moved onto the purchase at accept (S2.2.6 must do it; `Document` has no pending owner type yet).
Update 2026-10-02: the UI now uses these endpoints (New Items list, Accept, Dismiss with Undo, Add Details via `complete`, nav count badge). Receipt uploads set the dedupe key (S2.2.6); email capture does not yet (S2.2.2, S2.2.4). Not done: a Dismissed view with Restore (only Undo right after dismissing).
