# S2.4.6 Read a PDF from its text, not its page images

**Feature:** F2.4 Photo and document reading  
**Phase:** v2  
**Milestone:** M7 (proposed)  
**Depends on:** S2.4.1; S2.4.3 (to show it reads as well); S2.4.4 (the same checks apply)  

As the **builder**, I want a PDF that already contains its text to be read from that text, so a receipt that was emailed or saved as a PDF reads faster and costs less, with no loss in accuracy.

## Why
Today every PDF page goes to the model as an image (`DocumentReaderService` sends the pages as they are). Most PDFs from stores and order pages carry a real text layer, which can be pulled out for free in milliseconds. A text-only call is much cheaper and quicker than page images. Phone photos are not helped by this (they need OCR, which is a separate and weaker option), so this is for PDFs only.

## Acceptance criteria
- Text is taken from the PDF with a managed library (for example PdfPig), in-process: no new service, no native install on Render.
- The text is used only when it is good enough: enough characters per page, mostly readable (not garbage from a scanned image wrapped in a PDF), and it contains the kind of things a receipt has (an amount, a date). Otherwise the pages go as images, exactly as today.
- When the text is used, the model is sent the text (in page order, with page breaks marked) and the same list of properties, and gives the same answer shape: value, quote, page, confidence.
- Everything after the reading is unchanged: `Tidy`, `ReadingChecks` (S2.4.4), the result cache, the cost ledger and the daily caps. The ledger records that the text path was used, and the input and output tokens, so the saving can be seen.
- A PDF with several pages, or several PDFs read as one receipt, can mix: pages with text go as text, pages without go as images, in order.
- If the text path fails for any reason (parse error, password-protected, oversize), it falls back to images and the upload is not affected.
- The prompt version changes for the text path, so cached readings from the image path are not reused wrongly and the two can be compared.

## How we know it works
- Unit tests with sample PDFs: a text receipt uses text; a scan-only PDF falls back to images; a corrupt PDF falls back; mixed pages keep their order. No model call (fake provider).
- Measured with the labelled set (S2.4.3): the same PDFs read by the text path and the image path, fields right and cost per reading compared. The text path is kept only if it is no worse on the critical fields (store, date, total, item price, brand, model).

## Not in this story
- Skipping the model altogether when a PDF's text parses cleanly. That needs vendor-specific layouts and real receipts to test against, and a wrong total that looks sure is worse than a slow right one. Revisit once there is data.
- OCR for phone photos (Tesseract or similar): heavy to run, and less accurate than the model on crumpled receipts.
- Order emails, which already have a deterministic parser (S2.2.2).
