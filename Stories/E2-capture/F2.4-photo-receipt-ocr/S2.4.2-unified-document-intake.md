# S2.4.2 One intake for every document

**Feature:** F2.4 Photo and document reading  
**Phase:** v2  
**Milestone:** M6 (proposed)  
**Depends on:** S2.4.1 (Document reader); S2.2.2 (Receipt extraction); S9.9.6 (Attach a document to an item)  

As a **user**, I want any document I hand over to be read the same way, wherever I hand it over, so I never have to say what it is or retype what is on it.

## The rule
All documents are treated the same. We read the document, classify it, and mine it for data. It does not matter whether it arrived by email, by upload in New Items, by attaching it in the Add form, or by attaching it to an item.

## Acceptance criteria
- **Classify first.** Every document is classed as one of: order confirmation, receipt, warranty document, insurance policy, manual, or just a document. The class is stored with the file and the person can correct it.
- **Mine for the same core facts, whatever the class:** brand, model name, model number, price, date (plus store, order number and the list of items when present). What the document does not say is left empty, never guessed.
- **Order confirmations are kept.** They carry little data, but they are a strong signal that something happened (a purchase is coming). They create or update a New Item like any other document; a later receipt, shipping email or invoice for the same order joins it.
- **One intake, one set of rules** (the same for every entry point):
  - Fill only what is blank. Never overwrite something the person typed.
  - A high or medium reading goes in as read. A low one is flagged for the person to check before it counts (S2.2.2 "not sure" rule).
  - A name is not required to attach a document. If the document names the item, that is the name.
  - On an existing item the person sees what the document would change (before and after) and confirms, as for plans and policies today.
- **Warranty documents and insurance policies** take a second, specialised read for their own fields (terms, dates, limits, claim contacts), reusing the existing kinds. Manuals add serial number and registration deadlines the same way.
- **Cost.** One cheap read classifies and mines the core facts; the specialised read runs only for the classes that need it. Cached by file hash like today.
- **Every entry point uses it:** New Items upload and scan, forwarded email (body and attachments), the Add form, the item page, the purchase page.

## Why
Today the person picks the kind up front, only the New Items upload path reads anything, and attaching a file in the Add form or on an item page just stores it. A receipt attached to an item gave nothing, and the form insisted on a name. One intake removes that: the document speaks for itself.

## Not in this story
- Reading the web for terms nobody uploaded (S3.2.5, "find these terms").
- Multi-item orders becoming one purchase with several items (separate story).

## Status
Not built. Found 2026-10-06: the model has never been called from the app (the usage table is empty); an attached receipt in the Add form is only stored; the receipt kind has no brand, model name or model number.

Built so far 2026-10-06 (API and UI, tested, not browser-checked): the `document` kind (`document-kinds.json`: class, store, order number, date, total, item price, tax, card, items, brand, model name, model number) and the receipt read on a New Items upload now uses it (`Ai:Provider` real model or the QA stand-in). `DocumentClasses` normalises the class. A pending item stores `DocumentClass`, `ModelNumber`, `ItemPrice` (migration PendingFacts, applied to dev and test); the brand is matched to a known brand, the name is "brand + model name", and quick add carries the model number and item price to My Items. Stores are matched by normalised name ("Amazon.com" = Amazon, "SAMS CLUB #6452" = Sam's Club). New Items shows the class ("Order confirmation") and the Add form fills the model number and the item price (the order total only when no item price was read).

Reconciliation rules are built and unit-tested (`FactResolver`, 22 tests) but not wired to any screen yet: shared data first, then a confident reading, then what was typed, then a low reading. A spelling difference is corrected silently to the known form; a real difference is put to the person with the better-supported value pre-selected (the document when it was read with high confidence, what was typed when it was only medium). Names at least 80% alike (`SameNameSimilarity`) count as the same name; below that the person is asked.

Not built yet: the second, specialised read for warranty documents, policies and manuals; the image preparation step (a blur check before spending a read; crop and straighten later); reading on the Add form and the item page (the before-and-after confirm using `FactResolver`); forwarded-email attachments; letting the person correct the class.

Built later 2026-10-06 (API and UI, tested, not browser-checked): one stateless endpoint, `POST /api/document-facts/propose` (files plus the values a screen has), reads the document with the `document` kind and returns proposals using `FactResolver` (fill, correct a spelling to the shared-data form, or ask with the better-supported side pre-selected; store and brand matched to known parties by normalised name, `PartyMatcher`). The Add form reads each file when it is attached and the item page reads each file chosen in edit mode; both show the shared `document-facts-review` panel ("What we found in your document": ticks, what differs, "not sure" flags, unknown stores and brands shown but not ticked) and apply only the ticked values (on the form, or with the existing item and purchase updates). The item's own name is only filled when empty. A date still at its default (today) on the Add form counts as empty. Image preparation: `IImageProcessor.Sharpness` (edge spread at 1000 px) with a cutoff of 3.0 calibrated on the sample receipts (readable 4.5 to 47, blurred copies 0.9 to 2.8); a blurry photo is refused on the propose endpoint with "too blurry to read ... retake it", and on a New Items upload the item is still made, blank, with that note and no model call. Crop and straighten are not built.
Still not built: the specialised second read (warranty documents, policies, manuals); forwarded-email attachments; correcting the document class; reading a file that is already stored on an item (only files chosen now are read); only the first item of a multi-item form is compared.

Built 2026-10-06 (late): files already stored on an item can be read (`POST /api/document-facts/propose-stored`, "Read it" on each stored photo or PDF in edit mode); a PDF or photo attached to an order email (up to 3, 4 KB to 10 MB, not inline images) is kept with the pending item and read into it, and a receipt attachment upgrades an order-confirmation class to receipt; an email's own stage sets its class (confirmation = order confirmation, receipt = receipt); the review panel points a warranty document to /plans/new and an insurance policy to /insurance/new. Tests: API unit 298, integration 366; UI 706.

Built 2026-10-07 (API and UI, tested, uncommitted): the specialised read for a manufacturer's warranty document. New kind `maker_warranty` (length in months, counted-from, covers, exclusions, claim steps and contacts). On the item page a document classed warranty_document is applied at once: `POST /api/document-facts/warranty-stored` (stored file) or `/warranty` (file chosen now) replaces the item's maker warranty with a whole-product coverage from the purchase date (source Extracted), unless the length was read with low confidence or is not one clear number. The person says how they got it (came with the product / downloaded from the maker's website / not sure), recorded in the coverage terms; changing it rewrites the same coverage. Not built: warranty parts (components) from a document, crowd evidence from the document, counting from registration.

Built 2026-10-07 (later, uncommitted): parts from a warranty document (`parts` property: part | parts months | labor months) become their own Component coverages through the S3.2.8 code (`CoverageComponents.Build` now takes plain values). Sharing slice (now S6.1.6, reopened 2026-11-04: redaction preview, skip, account-level off switch and withdraw are required and not built): a ticked-by-default Share checkbox on the result card offers the policy facts (terms, parts, how it was got; never the file) as one pending `CandidatePolicy` per account, brand and category with a fingerprint of the facts; re-applying replaces it, unticking withdraws it. NOT built: the account-level Contribute setting, withdrawal after account deletion, the three-account count, operator verification (S6.6.3), the source re-check (S6.6.4).

Built 2026-10-07 (night, uncommitted): the document is compared with the shared warranty before anything is offered (`WarrantyDocumentService`, `WarrantyComparer`). Held = the lookup for the brand, category and model (a fake placeholder counts as nothing). Same as a VERIFIED one: applied to the item, coverage points at the policy, nothing offered or kept. Same as an unverified one: offered as `agrees`. Different length, or a part we do not hold or hold at other months: offered as `differs` (payload carries the policy it disagrees with) and the item still uses the person's own document. Nothing held: `new`. The result card says so. Parts on file that the document does not list are ignored. Still not built: the operator queue that reads these, the three-account count, the Verified-pending wording on the policy screens.
