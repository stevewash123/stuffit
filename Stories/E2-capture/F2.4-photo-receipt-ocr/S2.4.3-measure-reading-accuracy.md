# S2.4.3 Measure how well documents are read

**Feature:** F2.4 Photo and document reading  
**Phase:** v2  
**Milestone:** M6 (proposed)  
**Depends on:** S2.4.1 (Document reader), S2.4.2 (One intake)  

As the **builder**, I want a number for how accurately receipts are read, so a change to the instructions or the model is judged by a score and not a feeling, and so each kind of document uses the cheapest model that is good enough.

## Why
The real model has hardly been called from the app. `QaAiProvider` and the test fake return canned answers and never look at the file, so today nothing tells us whether the reader gets the date, total or model number right, or what a good-enough cheaper model would cost us in accuracy.

## Acceptance criteria
- **A labelled set** of about 40 to 50 real receipts, order PDFs and photos (clean, creased, dark, long, two-part), each with the correct store, date, total, tax, item price, brand, model name and model number written beside it. Kept outside the repository if it holds personal data.
- **An eval command** (`--read-eval <folder>`, Development only, in the style of `--email-parse-report`) reads every file through the real provider and prints, per field, how often it was right, wrong or missing, plus cost per document and the files that failed. It can write a CSV.
- **Opt-in.** It runs only when asked, spends real money inside the existing daily cap, and is never part of the standing suite.
- **Compare models.** The same set can be run against two models or two prompt versions and the scores shown side by side.
- **Pick models from the scores.** `Ai:ModelByKind` is set from the result. Until then development uses a cheap model (Haiku for receipts and documents, Sonnet otherwise) and the larger one is for the kinds that need it.
- **Prices are complete** for every model in use, so the cost the ledger shows is right.

## Not in this story
- Changing what is read (S2.4.4) or how photos are prepared (see F2.4 "Later").

## Status (2026-10-16): first version built
- `--read-eval <folder> [--truth truth.json] [--model m]... [--kind document] [--raw] [--limit n] [--out csv]` is in `Program.cs`, scoring in `Infrastructure/Ai/ReadEval.cs`. It uses the real clean-up and `DocumentReaderService` with an in-memory ledger (no database, no cache), and the real provider.
- Answer key and photos: `Testing/SampleData/receipts/paper-photo/` (4 phone photos, `truth.json`). The laptop's 25 synthetic PDFs are still to be brought over.
- First run (4 photos, `document` kind): Sonnet 5.5 92% of fields, Haiku 5.5 89%, 0 wrong, 0 flagged, with or without the clean-up. The only consistent miss is `item_price` on multi-item receipts, because the property says to leave it empty when several items are listed; that is a prompt problem (document-v2), not a reading problem.
- Still to do: more files (the PDFs, more photo kinds: faded, dark, long), the price for Haiku 5.5 in `Ai:Prices`, then set `ModelByKind` from the scores.
