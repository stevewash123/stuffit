# S2.4.1 Document reader: find a list of properties in a scanned document

**Feature:** F2.4 Photo receipt capture  
**Phase:** v2  
**Milestone:** M6  
**Depends on:** S7.6.5 (LLM integration and cost control); S2.1.2 (Attach receipts, manuals, photos); S2.6.2 (Strip location data and shrink photos on upload)  

As a **system**, I want to give a vision-capable model one or more pages (a photo, a scan or a PDF) plus a list of the properties wanted, and get back what the document says about each, with where it says it, so every feature that reads a document uses one reader instead of its own.

## Who uses it
One service, many document kinds. Each caller names a kind and gets that kind's property list:
- Receipts and order documents (S2.2.2, S2.2.6, S2.4.2)
- Warranty and home protection contracts, and terms of service (S3.4.2)
- Insurance policies and declarations pages (S3.4.1)
- Manuals, nameplate photos and registration cards (S2.7.4)
- Card terms and policy pages (S6.1.2, S6.1.3)
- Warranty paperwork that asks for an action, for reminders (S4.6.1, the "register within 30 days" case)

## Acceptance criteria
- **Input.** One or more files (PDF, JPEG, PNG, WebP, HEIC after conversion), in page order, treated as one document. Scanned pages and PDFs with real text both work, because the model reads the page images directly; no separate OCR step is needed to start. Large photos are already shrunk (S2.6.2). A document over the model's page or size limit is split in page order and the pieces read in turn, never cut off silently.
- **The property list is data, not code.** Each document kind has a list of properties kept as data (in the database, edited without a release). A property has a key, a label, a type (text, date, money, number, yes/no, choice, list, phone, website), a one-line description that tells the model what to look for, and whether it is required. Adding a property or a kind is a data change.
- **Instructions and examples, not training.** The model is not trained or fine-tuned. A property list is the instruction, and accuracy comes from clear property descriptions plus a few worked examples (a real document and its correct answer) kept with each kind and drawn from the test set. A fixed, familiar list (price, item number, names, dates) is an advantage: the list stays stable while layouts vary a lot between vendors, and reading varied layouts is what the model is for.
- **Deterministic first, model for the rest.** Where a source is regular (an order email from a known store, as `ReceiptEmailParser` already reads), the plain parser runs first and is exact and free. The model fills only what the parser left empty, or handles the documents no parser fits. Per-store hints (where this store prints its order number) can be added as examples without code.
- **A second mode: find these terms.** The caller can instead pass an ad hoc list of terms ("auto-renewal", "waiting period", "cancellation fee") and get, for each, whether the document addresses it and what it says. This is how "does this contract have a waiting period?" is answered without a new property.
- **Every answer carries its evidence.** For each property: `found` (yes or no), the value in the property's type, the quote copied from the document, the page number, and a confidence (low, medium, high). A property the document does not state comes back as not found, with no value. The model is told never to guess, infer from the company's reputation, or fill from general knowledge.
- **Structured output.** The reply is constrained to the property list's shape (the API's structured output), so it always parses. The quote and the page are fields of that shape. The API's separate citations feature cannot be used together with structured output, so quotes are part of the schema instead.
- **Checking the quote.** For a PDF with real text, the quote must be found in that text; one that is not is marked unverified. For a scan, there is no text to check against, so the screen shows the page image next to the value and the user is the check. Either way, a value is never accepted without the user seeing it (S3.4.2, S9.9.2).
- **Sanity checks after reading.** Dates in a plausible range, an end after a start, phone numbers and web addresses well formed, money not negative. A value that fails is kept but flagged.
- **The document is data, never instructions.** Text inside a document that tries to give the model instructions has no effect. The reader has no tools, can only return the shape above, and its output is validated before anything uses it.
- **Choice of model per document kind, set in configuration.** A small, fast model for short receipts and a stronger one for long contracts, decided by measuring accuracy and cost on real samples (see the test set). Changing a model is a configuration change.
- **Cost and limits.** Every call is logged with the account, document kind, model, pages and tokens used, and its cost. The per-account and global caps of S7.6.5 apply. The same file read twice for the same property list returns the stored result (by content hash). Work that is not urgent (reading a backlog) can run as a batch at lower cost. Over the cap, or on any failure, the caller gets "not read" and the user fills the form by hand; reading never blocks saving.
- **Runs in the background.** The request returns at once with a reading status; the screen shows "Reading your document…" and stays usable, then fills in when the answer arrives.
- **Prompts are versioned,** with the version stored on every result, so a result can be traced to the instructions that produced it.
- **Privacy.** Documents go to the model provider through its API; photos are cleaned of location data first (S2.6.2). The privacy policy says so plainly, and states the provider's data retention and training terms as they actually are at the time of writing, checked against the provider's current published terms. The reader keeps the extracted result with the pending item or plan, not a second copy of the file.

## Starter property lists (drafts, to refine against real documents)
- **Receipt or order:** store, order number, purchase date, delivery date, total, tax, payment method and last four digits, line items (name, model, quantity, price).
- **Warranty or home protection contract:** company, plan name, contract number, start date, end date or term, renewal terms and whether it auto-renews, price and billing period, service fee per claim, waiting period before coverage starts, what is covered, coverage limits (per item, per year, overall), exclusions, pre-existing condition terms, how to make a claim, time limit to file a claim, claim phone, claim website, cancellation and refund terms, whether it can be transferred, and any action required of the customer with its deadline.
- **Insurance policy or declarations page:** insurer, policy number, policy type, start and end dates, premium, deductible, personal property limit, special limits by kind of item, scheduled items with values, claim phone, claim website.
- **Manual, nameplate or registration card:** brand, model, serial number, manufacture date, warranty term, registration requirement and deadline, support contact.

## The test set (build this before trusting it)
Gather real samples of each kind (the user's own receipts, a home protection contract such as an American Home Shield one, an insurance declarations page, a few manuals), hand-label what each should return, and measure accuracy per property. A property ships to users only when it clears an agreed bar on that set; the rest stay as blank fields the user types. Keep the set as a regression test for every prompt or model change. Samples with personal details are scrubbed before they are kept.

## Not in this story
- The screens that show the results (S2.2.5 pending items, S3.4.2 plan form, S9.9.2).
- Reading handwriting reliably, or receipts photographed badly enough that a person could not read them.
- Training or fine-tuning a model.

## Status

Core built 2026-10-03, with the AI service (see S7.6.5): the property lists as data in `Ai/document-kinds.json` for receipt, warranty or home protection contract, insurance policy and manual (draft lists), `DocumentKindCatalog`, the request and result types with evidence (value, quote, page, confidence, and an issue when a value fails its type), the Anthropic provider and fake, and the wrapper's cache, caps, validation and fallback. Ledger tables (`ai_usage`, `document_readings`) and the endpoint that reads already-uploaded files (`POST /api/document-readings`, `GET /api/document-readings/kinds`) built 2026-10-05 and tested (see S7.6.5). Not built: reading bytes that are not stored yet (an upload that keeps no copy, for S3.4.1), reading a plain-text PDF's own text to check quotes, splitting a document over the page limit, the ad hoc "find these terms" mode, running in the background with a status, the labelled test set, and any screen using it. Nothing has been run against the real API.
